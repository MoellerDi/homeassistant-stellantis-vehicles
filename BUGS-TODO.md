### 13. `get_programs()` only checks the double-n "preconditionning" API spelling (`upstream/develop`)

`base.py:342` on `upstream/develop`: `air_conditioning = (self.data.get("preconditionning") or {}).get("airConditioning") or {}` - only reads the double-n key. Stellantis' API spells this section's key inconsistently: some accounts report `preconditionning` (double n), others `preconditioning` (single n) - confirmed by this fork's own history (see below).

Update: a real `/status` response captured 2026-09-23 (debug log, this fork) shows **both keys present at once**, with identical content duplicated under each spelling: `"preconditioning": {"airConditioning": {"status": "Disabled", ...}}` and `"preconditionning": {"airConditioning": {"status": "Disabled", ...}}`. So the failure mode isn't necessarily "each vehicle reports exactly one spelling" as originally assumed (see the note on #14 below) - at least some accounts get both, redundantly, which would make neither #13 nor #14 actually trigger for them. Single data point though (one vehicle/account), so the actual distribution across accounts - both-always, one-or-the-other, or a mix - is still unconfirmed.

`get_programs()` builds the program payload that `send_preconditioning_command` posts back to the vehicle (`/ThermalPrecond`) on every start/stop press - it always sends *all four* program slots, using the current ones as a base. For a vehicle reporting under the single-n key, `get_programs()` sees no data and returns the all-disabled default placeholders instead of the vehicle's real schedule. Pressing "start" or "stop" preconditioning then **silently overwrites and erases** the user's actual configured programs on the vehicle.

Already fixed, but only on the still-unsubmitted `feature/writable-preconditioning-programs` branch (commit `43b059c`, not an ancestor of `upstream/develop`), which introduced a `preconditioning_data` property doing `self.data.get("preconditioning") or self.data.get("preconditionning") or {}` and is used consistently there. See also #14, the same root inconsistency biting a different code path in the opposite direction.

Fix sketch: check both spellings in `get_programs()`, e.g. `(self.data.get("preconditioning") or self.data.get("preconditionning") or {}).get("airConditioning") or {}`.

### 44. A denied event topic makes `_on_mqtt_subscribe` reconnect MQTT every 300 s, forever (`upstream/develop`)

`stellantis.py` (`_on_mqtt_subscribe`) on `upstream/develop` and `testing`.

`_on_mqtt_connect` subscribes to the response topic plus one `MQTT_EVENT_TOPIC + vin` per vehicle. If the broker denies any of them in the SUBACK (`0x80`), `_on_mqtt_subscribe` schedules `reconnect_mqtt()` 300 s later, no matter which topic was denied. The reconnect requests the same topics again, so an account that isn't entitled to the event topic is denied again on every attempt: an endless reconnect cycle every 5 minutes, each one briefly dropping the response topic and with it the remote commands. This is the realistic shape of the invalid #15 (a per-topic denial in the SUBACK, not a refused connection).

Upstream only subscribes to the event topic and drops its messages, so the cost of retrying it was never weighed against anything. With PR #650 the event topic feeds the live updates, which makes it worth getting right. The `mqtt_live_updates` option from #650 already works as a workaround: turned off, the event topic isn't requested at all.

Fix sketch: since PR #667, `_on_mqtt_subscribe` knows the topic of the SUBACK (`self._mqtt_subscriptions`). Only reconnect when the response topic is denied. For a denied event topic, log one WARNING naming the topic and skip it on later connects for this session (an in-memory flag reset on reload, not a stored option), so commands keep working and the live updates fall back to REST polling.

### 48. `async_remove_entry` removes other config entries that are not `LOADED`, and skips the removed entry's own files when another entry exists

Fixed on the local branch `bugfix/remove-entry-keeps-other-entries` (from `upstream/develop`, one commit `fc4af60`, plus the local-only `bugfix/remove-entry-keeps-other-entries-tests` with 21 tests). Not pushed, no PR yet, not in `testing` (taken out again on 2026-10-07 at the user's request).

`__init__.py`, `async_remove_entry`. The "is this the last entry" check used `hass.config_entries.async_loaded_entries(DOMAIN)`, which only returns entries in state `LOADED`. An account in `SETUP_RETRY` (Stellantis outage) or `SETUP_ERROR` (waiting for reauth) counted as gone, so the block below it removed it together with the deleted entry (loop "Remove any remaining disabled or ignored entries", introduced in `4b85f92`, 2025-05-09, no recorded rationale). The same block also removed the JS card URL, and it was the only place that cleaned up the deleted entry's own OTP file and image folder, so deleting entry A while entry B existed left A's files behind for good (`customer_id` of A is never seen again).

Decisions on the branch:
- Any other entry that is not ignored counts as remaining, a disabled one included (it keeps its configuration and can be enabled again). Only then the card URL is removed.
- Nobody else is removed any more, ignored entries included (this integration has no discovery, so they hardly exist).
- The OTP file is kept while another entry has the same `customer_id`, otherwise it is deleted (the file cannot be recreated without a new SMS code). See #47 for why sharing can happen at all.
- Pictures are deleted per VIN of the removed entry's devices (the VINs are already collected for the repair issues). The image folder goes with its leftovers when the account is not shared, otherwise only once it is empty. `shutil.rmtree` stays, always behind an emptiness or "not shared" check.
- A missing `customer_id` no longer crashes the cleanup (`.replace(...)` with `None`).

Known leftovers, not fixed: the static path of the card stays registered and the card URL is only added in `async_setup`, so after deleting the last entry and adding a new one the card is missing until the next restart. A VIN that appears under two entries of one account loses its picture for both until the next reload.

### 47. OTP file and image folder are keyed by `customer_id`, so config entries of the same account share one OTP state

Status 2026-10-07: not reproduced, no change planned. Waiting for a follow-up in upstream issue #601 or a new ticket from its reporter (ac-uy). Verified by reading the code only, nothing was checked against the Stellantis/InWebo side.

Where: `OTP_FILENAME = "{#customer_id#}_otp.pickle"` (`const.py`) gives `.storage/stellantis_vehicles/<customer_id>_otp.pickle`. The path is built in `get_otp_code` (`stellantis.py`) and in `async_remove_entry` (`__init__.py`). Pictures live in `www/stellantis_vehicles/<customer_id>/<vin>.png`.

How entries end up sharing it: since `f360215` (2026-09-13, issue #601) the unique_id is `<customer_id>_<mobile_app>_<country_code>`, so a MyCitroën and a MyPeugeot entry of one login can coexist. The reporter confirmed both load on 2026.9.4 and 2026.10.1-beta.1. That Stellantis returns the same `customer` for both brand apps is not verified (the issue itself says so), but the rejected second setup that motivated the change points that way. Entries created without remote commands get a synthetic `MN-<uuid>` id and are never shared; older entries can carry a real customer_id even with remote commands off.

What the file holds: a pickled `Otp` object with the InWebo device state (`device_id` = first 16 characters of the OAuth access token at activation time, a random `iwalea`, and the `IWData` keys). Every code generation runs `IWData.synchro`, which replaces `iwK0`/`iwK1` (`iwK1` as a hash chain with `dK1`), and then the whole object is pickled back. The runtime loads the file once (`self.otp is None`) and keeps the object in memory afterwards.

Failure mode, derived from the code and not observed:
1. The second entry's SMS activation registers a new InWebo device and overwrites the first entry's file (no check for an existing file). The first device stays registered at InWebo and counts towards `NOK:MAXNBTOOLS`.
2. Until the next restart both entries keep their own in-memory copy and overwrite the file at each code generation (about every 3 days, the MQTT refresh token lives 3 days).
3. After a restart both load the last written state, so two copies of one device advance independently. Because of the hash chain the stale copy is probably rejected by the server (`invalid_grant`, `ConfigException`, "OTP code is empty"), which is exactly the failure class that disables remote commands (see #19).

Upstream issue #601 itself suggested namespacing OTP and picture storage per config entry; the shipped change only touched the unique_id. Our removal fix (#48) keeps the OTP file while another entry shares the `customer_id`, but that only covers the delete side.

Fix direction: key the OTP file by `entry_id`. Not trivial: the migration has to give the second entry its own device (a new SMS code and PIN), two entries must never copy one device. The pictures could follow, but they are regenerable and of little value; if both contexts expose the same VIN, #601 asks for one deterministic owner.

To verify once there is data: two entries of one account with remote commands on. Compare the first 5 characters of both `customer_id`s, the mtime of the pickle against the refresh times, and look in Graylog for `invalid_grant` or `OTP` messages around restarts.

### 50. `send_command` returns normally when nothing was sent

Fixed on the local branch `bugfix/command-send-failures` (second commit `fe3a973`, together with the automatic charge stop fix of #4, plus `bugfix/command-send-failures-tests`). Not pushed, no PR yet, not in `testing`.

`base.py`, `send_command`. `send_mqtt_message` returns `None` when the publish returned an error code and raises `ConfigEntryAuthFailed` when the login is rejected. `send_command` ignored the first and swallowed the second (it only started a reauth), so both looked like a sent command to the caller: a button press showed no error, and the automatic charge stop set `_manage_charge_limit_sent` although nothing left the integration.

The fix: the `try` now wraps only the send call. In both cases `send_command` logs an error and raises `HomeAssistantError` with the translation key `command_not_sent` ("Cannot send "{name}" to the vehicle. See the log for details."). The history entry and the pending-command lock are only written for a command that was really published. Texts exist in en, de, it and fr (it and fr are not checked by a native speaker, the maintainer is Italian), other languages fall back to English. `feature/writable-preconditioning-programs` adds six keys behind the same `command_already_pending` entry, so merging it with this change gives a trivial text conflict in four translation files (keep both), accepted.

Why it ships together with #4: the automatic stop runs inside `_async_update_data`, and without the `try/except` from that commit the new exception would fail the whole update. Checked with a throwaway test: on the `send_command` commit alone both a failed publish and a rejected login fail the update, on the auto stop commit alone the flag is set although nothing was sent. The two commits stay separate on purpose, one PR.

Decision: no persistent notification for this case. `command_error` is created when the vehicle answers with a failure (the command was sent), `reconfigure_otp` already covers the rejected login, and `hass_notify` uses a new `uuid4` id each time, so the automatic stop retrying every minute would flood the list.

Open, not done (stage 2): confirm that the vehicle executed the command, not only that it was published. The answer arrives via MQTT (`COMMAND_STATUS_SUCCESS = ("0", "1")`, `COMMAND_STATUS_STILL_IN_PROGRESS = ("900", "901", "903")`, `update_command_history`). The automatic stop would remember the `action_id`, wait while the command is in progress and resend after a failed status or a timeout, with a cap on attempts. The stop is an idempotent delayed charge program, so a resend is harmless. Parked until Graylog shows which codes a `/VehCharge` stop really returns; `901` is skipped in `_on_mqtt_message` and never reaches the history.

### 4. `_auto_stop_charge_at_limit` can crash with `AttributeError`/`TypeError`

`base.py:583-602` (`_auto_stop_charge_at_limit`) calling into `base.py:389-396` (`send_charge_command`).

`send_charge_command` does `current_hour.hour` / `.minute` without a `None` check. The manual "stop charging" button is guarded (`button.py:171` requires `time_battery_charging_start` to be set), but the automatic charge-limit-stop path isn't, so it can crash the whole coordinator update if that sensor is `None` while charging.

A second, narrower trigger in the same function: `base.py:598`, `int(float(self._sensors.get("battery"))) < int(charge_limit)`, assumes `"battery"` is never `None` once the key is present in `self._sensors`. `get_value()` (`base.py`, around the `_coordinator._sensors[key] = value` assignment) only skips overwriting an existing entry when the *new* reading is `None`, so the key can hold `None` if the very first status response after startup had `battery_charging == "InProgress"` but no `battery` field yet - `float(None)` then raises `TypeError`.

Fix sketch: same `None` guard as the button's `available` check, before calling `send_charge_command` from `_auto_stop_charge_at_limit`; add an equivalent guard for `self._sensors.get("battery") is None` right next to the existing `charge_limit_on and charge_limit and "battery" in self._sensors` check. There's a stale, unmerged branch `bugfix-not-ready-yet/charge-command-missing-start-time` that touches the same area but predates the preconditioning-programs refactor and doesn't cover either of these call sites - needs a fresh implementation, not a rebase.

Update 2026-10-07: fixed on the local branch `bugfix/command-send-failures` (first commit `10a6142`, plus the local-only `bugfix/command-send-failures-tests` with 28 tests), which carries this fix and #50 together as one planned PR. Stage A: both `None` cases are guarded (battery, charging start time, with a comment why a missing start time is a normal state, logged at debug level only) and the send is wrapped in `try/except (HomeAssistantError, CommunicationError)`: a failure is logged as a warning, the flag stays `False` and the next poll retries instead of failing the whole update and discarding the fresh data. Not pushed, no PR yet, not in `testing`. The earlier separate branches `bugfix/auto-stop-charge-limit-errors` and `bugfix/send-command-reports-unsent-commands` are deleted (content is part of the new branch, last commits `10a6142` and `f6c312c`, tests `4844ea7` and `95ef6db`). The stale branch `bugfix-not-ready-yet/charge-command-missing-start-time` (last commit `412a3d2`, tests `d73cfa8` were local only) is deleted locally and on `origin` (the first `git push --delete` failed twice with HTTP 500, the API with 403, a later retry on 2026-10-07 went through).

Still open, deliberately not part of stage A: (B) the check reads `self._sensors`, which the entities only fill after the coordinator update, so it works with the previous cycle's battery level (harmless for AC, a few percent on DC, up to an hour with a long `number_refresh_interval`); (C) a failed command result never resets `_manage_charge_limit_sent`, and the vehicle's execution of the stop is not confirmed, see the open stage 2 in #50.

### 20. `battery` sensor can stay stuck at 100% while `battery_residual`/`battery_capacity` reflect a real partial charge (`upstream/develop`)

`const.py:196-202` (`battery` entry, `"value_map": ["energies", {"type": "Electric"}, "level"]`) reads the vendor-reported percentage directly with no cross-check against the energy-based fields. `base.py:677-687` already special-cases one narrow symptom of the same underlying vendor bug (PR #476): if `battery > 90` and `autonomy == 0` (read from `["energies", {"type": "Electric"}, "autonomy"]`), it forces `battery` to `0`. That only catches the complete-depletion-but-100%-shown case, not the more general mismatch reported in upstream issue #535: `level` pinned at 100% while `battery_residual`/`battery_capacity` (`const.py:243-260`) report a real, nonzero partial charge (e.g. 12.15 of 52.70 kWh, ~23%).

Confirmed independently by multiple e-CMP-platform EV owners (Peugeot e-2008 and others) in [issue #535](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/issues/535), still open. Reporters say Stellantis support has acknowledged the backend data issue but it remains unresolved on their side.

Fix sketch (as suggested in the issue thread): in `get_value()`'s `key == 'battery'` branch, after the existing `autonomy == 0` guard, add a fallback that compares the reported `level` against a computed `(battery_residual / battery_capacity) * 100` - reading both from the raw payload via `get_value_from_map`, the same way `autonomy` already is, since sensor evaluation order doesn't guarantee `self._coordinator._sensors` already holds them - and prefer the computed value when it's meaningfully lower than the reported one. Same caution as the existing `switch_battery_values_correction`/`KWH_CORRECTION` workaround (issue #272): this patches around a vendor data-quality bug rather than a bug in this integration's own logic, so it probably belongs behind an opt-in toggle rather than unconditional, to avoid overriding a legitimately-100%-charged vehicle if residual/capacity ever report noisy or rounded values near the top of the range.

### 14. `binary_sensor.preconditioning`'s `value_map` only checks the single-n "preconditioning" spelling (`upstream/develop`)

`const.py:443-444` on `upstream/develop`: `"value_map": ["preconditioning", "airConditioning", "status"]` - the generic sensor-value lookup (`get_value_from_map` in `base.py`) reads `vehicle_data["preconditioning"]` directly, the opposite spelling from #13's `get_programs()`. For a vehicle reporting under the double-n key (the spelling this fork's own comments call the more common one), `get_value_from_map` never finds a value, so `StellantisBaseBinarySensor.coordinator_update` hits its `if value is None: return` early-out and the `binary_sensor.*_preconditioning` entity never updates off its restored/default state.

Originally assumed no vehicle could satisfy both #13 and #14 at once, since they check opposite spellings. That assumption doesn't hold: a real `/status` response (see the update on #13 above) shows both `preconditioning` and `preconditionning` present simultaneously, with identical duplicated content, for at least one account. For an account like that, both #13 and #14 read valid data and neither bug actually fires - the "exactly one breaks" framing only applies to accounts that report a single spelling exclusively, and it's unconfirmed how common that is versus the both-keys case.

Fix sketch: harder to fix with a one-liner than #13, since `value_map`-based sensors have no built-in "try key A or key B" mechanism. Either extend `get_value_from_map` to accept alternate keys at a position, or special-case this one sensor to read through a small helper that checks both spellings.

### 37. A token refresh never reaches the running paho client, and a refused MQTT connect never triggers a refresh

`stellantis.py:1100-1108` (`_on_mqtt_disconnect`) on `testing`, same code on `upstream/develop`.

`_on_mqtt_disconnect` only refreshes the MQTT token on `result_code == 11` (`MQTT_ERR_AUTH`). paho never delivers that code: with the v1 callback API this integration uses, every refused CONNACK (codes 1-5, including 4 "bad username or password" and 5 "not authorized", i.e. an expired or revoked access token) is turned into `MQTT_ERR_CONN_REFUSED` (5) before `on_disconnect` runs. `MQTT_ERR_AUTH` only appears in paho's `error_string()`, no client code path returns it (checked against paho-mqtt 2.1). The refresh branch is dead code.

Since PR #653 (`b7e715b`, merged upstream), `_on_mqtt_connect` sees the real CONNACK code and returns early on a refusal, so that is the one place that still knows *why* the connection was refused; in `on_disconnect` it is already collapsed to 5, indistinguishable from e.g. 3 "server unavailable".

Even a working refresh branch would not have been enough on its own: `refresh_mqtt_token_request()` only stores the new token in the config, while the running paho client keeps the password it was created with. Since #619 (`8acfeb2`, merged 2026-09-19) `_connect_mqtt` builds a new client for every (re)connect and `username_pw_set` is only called there, on the new client; before #619 the client object was reused and every `connect_mqtt()` set the stored token on it again, so the gap in this form exists since #619. It mostly goes unnoticed because the broker only checks the token on CONNECT (an established connection outlives its token) and every reconnect the integration starts itself (`connect_mqtt()` from the poll or before a command) builds a new client from the stored token. Only paho's own auto-reconnect reuses the stale one: the client is created with token T1, the scheduled refresh stores T2 while the connection stays up, then a network blip makes paho reconnect with T1. That case already heals itself: `get_vehicle_status()` runs every poll (60 s), sees `is_connected() == False` and calls `connect_mqtt()`, which builds a new client with the stored T2. It only stays broken when the stored token is invalid too (e.g. after a failed scheduled refresh), until the next scheduled refresh.

Live test 2026-10-05 (poll interval raised to keep the poll from rebuilding the client, MQTT blocked in the firewall until the token the client was created with had expired, with one scheduled refresh in between, then unblocked):

- With the fix (`bugfix/mqtt-token-refresh-updates-client`): paho's own reconnect of the same client was accepted (22:35:59 connect, 22:36:00 CONNACK, resubscribed).
- Without the fix, otherwise identical: paho's reconnects reached the broker (TCP up) and were dropped after 130-180 ms with `MQTT disconnected (code 7: The connection was lost.)`, on two different broker IPs, with no CONNACK at all (neither `MQTT connected` nor `MQTT connection refused (code N)`). Reloading the integration right after built a new client with the stored token, which was accepted immediately, so it was the token, not the network.
- The broker (AWS, eu-west-3) therefore does not answer an expired token with CONNACK 4/5 but closes the connection, like AWS IoT Core does. To paho that is indistinguishable from a network drop.

Earlier log history:

Graylog (2026-08-25..10-05) doesn't show this happening:

- All 1,030 refusals (`MQTT disconnected (code 5)`, in four bursts 2026-09-11..09-17, the longest 13 h 50 min) predate #619. Back then every poll handed the fresh stored token to the (reused) client, so they can't have been stale-token refusals. They match the connect race #619 fixed instead: the poll's `connect()` + `loop_start()` on the client while paho's own thread was reconnecting it, so the poll's CONNECT never got a CONNACK while paho's thread kept being refused every 2 minutes. Last refusal 2026-09-17 04:45 UTC, none since. The real CONNACK code was never logged (before #653 `_on_mqtt_connect` read the wrong argument).
- Since #619 there were 14 paho auto-reconnects; each either ran seconds after the client was created or failed with code 7 (network) before any CONNACK, and the next successful connect came from the poll's new client. No CONNECT with a token older than its lifetime reached the broker, so whether the broker would refuse one (and with which code) is still unobserved.
- Code 11 never appears, which confirms the dead branch.

Fix sketch, in two parts:

1. Root cause: at the end of `refresh_mqtt_token_request()`, after `_log_http_exchange`, hand the new token to the running client, `if self._mqtt is not None: self._mqtt.username_pw_set(MQTT_USERNAME, mqtt_config["access_token"])`. paho (checked against 2.1, the version HA pins) only stores `_username`/`_password` there and reads both again in `_send_connect()` on every CONNECT, including its own auto-reconnects (verified with a stub broker: the CONNECTs carried `token-1`, `token-2`, `token-2` after a mid-session `username_pw_set`), despite its docstring saying "must be called before connect()" (that refers to the current connection). Calling it from the event loop while the paho thread runs is fine: it only rebinds two attributes. `_send_connect()` reads `_password` twice (length, then packing), so a swap in that microsecond window with a token of a different length would malform one CONNECT and paho would simply retry. [PR #671](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/pull/671), branch `bugfix/mqtt-token-refresh-updates-client` (tests on `-tests`, local only), opened 2026-10-05; confirmed by the live test above.
2. Not feasible as sketched: the broker never sends CONNACK 4/5 for a bad token (see the live test), so a handler in `_on_mqtt_connect` would never fire, and `on_disconnect` only sees code 7, the same as a real network drop. ### 7. `StellantisLastChargeSensor` can raise `KeyError` at the end of a charge

### 21. `send_abrp_data` logs an undeduplicated warning on every failed ABRP push (`upstream/develop`)

### 40. The trips endpoint drops the start of the time range once a `pageToken` is sent

`GET connectedcar/v4/user/vehicles/{id}/trips`, used by `get_vehicle_last_trip` (`stellantis.py:805-821`, `upstream/develop`). A server-side bug, not one in this integration, but the integration relies on the broken part.

Measured on `testing` with the temporary `debug_fetch_trips_paging` action against the fork maintainer's vehicle, seven runs on 2026-10-02 (Graylog):
- Default page size is 60. `pageSize=30` is accepted, `pageSize=200` is rejected with `400 {"code": 40000, "message": "Invalid parameter: pageSize"}` (the limit in between was not probed). Pages carry `total`, `totalPage`, `currentPage` and `_links` `first`/`self`/`prev`/`next`/`last`. Within a page trips are sorted oldest first.
- The endpoint only keeps about two months: a query starting 2026-06-04 returned 2026-08-01 10:42 as its oldest trip.
- A closed range `timestamps={from}/{to}` works: 02.09.-17.09. returned one page with exactly the 47 trips that fall in that range.
- Page 1 is always right. Every follow-up page comes from the full list of available trips (oldest first, starting at 08-01), at offset page x page size, with the count capped at page 1's `total`. In other words the start of the range is lost:
  - 30-day window (`total` 87): page 2 returned entries 60-86 of the full list (08-17 to 08-26, all before the window); the 27 newest in-window trips were never returned.
  - 60-day window from 08-03 (`total` 190, twice): 8 trips lie between 08-01 and 08-03, so page 2 repeated the last 8 trips of page 1 and the 8 newest trips were missing.
  - 08-03 to 10-01 with `pageSize=30` (`total` 189): same 8-trip overlap on page 2 and the 8 newest in-window trips missing; neither the smaller page size nor the closed range helps.
  - 06-04 to 09-17 with `pageSize=30` (`total` 158): all six pages correct and gapless, because the start lies before the oldest available trip, so the filtered list and the full list begin at the same trip.
- Same result whether the `next` href is followed as-is (the vendor MyCitroën app's `TICRepository` does this) or the filtered URL is sent again with only the `pageToken` added (what `get_vehicle_last_trip` does). Whether the end of the range and `distance` survive on follow-up pages could not be told apart from the `total` cap.

Who is affected: any query with an effective start, i.e. `get_vehicle_last_trip` (start = now - 24 h) and the vendor app's incremental sync (start = last known trip), once there is more than one page. The third-party MyStellantis app queries without any filter and jumps to `last`, so its paging is consistent.

Impact today: with more than one page the `last` page `get_vehicle_last_trip` follows holds the wrong trips, so `trips[-1]` would be a wrong "last trip". Not reached in practice (at most 7 trips per 24 h window in the logs, far below 60). Any future feature that imports trip history by paging (the commented-out `get_vehicle_trips` caller in `base.py`) would silently get wrong and missing trips.

Fix sketch: in `get_vehicle_last_trip`, use only page 1 and log a warning when `totalPage > 1` instead of following `last`. For history there are two reliable ways: closed windows `timestamps={from}/{to}` small enough to fit one page (split a window and retry if `totalPage > 1`), or no start at all (only an end, or none) and then paging. Nothing older than about two months is available either way. Dedupe by trip `id` regardless.

### 46. OTP activation errors can still reach the log through `logger.error(xml)`, `ConfigException(xml)` and `requests` exception texts

Left over after the review of `otp/otp.py` for #24 (2026-10-06); all three are in the error path of the activation, not the normal OTP computation.

## Improvement ideas (not bugs, architecture/maintainability notes)

### 16. Shared aiohttp session is torn down on any request error, risking cascading failures

`stellantis.py`, `make_http_request` (`StellantisBase`). `self._session` is a single `aiohttp.ClientSession` shared by the whole account (all vehicles' coordinators poll through it concurrently). On *any* error - a timeout, a `ClientError`, an HTTP 5xx, even an unrelated unexpected exception - the `except` blocks call `await self.close_session()`, which closes the session object and sets it to `None`. If two coordinators are polling concurrently (the normal case for a multi-vehicle account) and one request fails, the session gets torn down out from under any other request still in flight on it, which would then fail too, unrelated to whatever actually went wrong. Not confirmed via a reproduction (would need a real concurrent-failure timing test), but the design is a plausible source of the kind of "everything broke at once, then recovered next poll" reports that are hard to diagnose from user-submitted logs.

Idea: stop closing the session on ordinary per-request failures. `aiohttp.ClientSession` already pools and recovers connections internally per request; forcibly recycling the whole session on every error is what creates the cross-request blast radius. Reserve `close_session()` for genuine shutdown (`async_shutdown`, already does this) rather than calling it from inside `make_http_request`'s exception handlers at all. If a specific error really does indicate a broken session (rare), that call site can close it explicitly instead of every error path doing so unconditionally.

Expected effects if implemented:
- Upside: fixes the cascading-failure risk; fewer needless TCP/TLS re-handshakes on transient errors (slightly lower latency, less load on Stellantis' servers); the session then lives for the whole config entry lifetime, which is the idiomatic aiohttp usage pattern. Also incidentally stops closing the session on `ConfigEntryAuthFailed`/`CommunicationError` (e.g. an expired OAuth token) - the session has nothing to do with token validity (the Authorization header travels per request), so that reset was never buying anything there either.
- No visible API/behavior change elsewhere: `make_http_request`'s return values and raised exceptions are unaffected, this is purely internal recovery mechanics.
- Main risk: today, *any* error self-heals by rebuilding the session from scratch on the next call - possibly masking rare cases where aiohttp's own connector doesn't cleanly recover a broken connection by itself (e.g. across a host-level network change like a Wi-Fi reconnect or VPN switch). Removing the blanket reset could turn one of those rare cases into "stuck until the integration is reloaded" instead of "self-heals on the next poll". Since this repo has no automated test suite (per its own `CLAUDE.md`), this needs manual verification against a running instance, ideally through an actual network interruption, not just a code read.

### 17. `get_value_from_map`'s implicit, untyped path lookup makes bugs like #13/#14 easy to introduce and hard to catch

`base.py`, `get_value_from_map` plus every `value_map` entry in `const.py`'s `SENSORS_DEFAULT`/`BINARY_SENSORS_DEFAULT`. The lookup infers what each path element means from its Python type at runtime (a `dict` selects a list item by field, an `int` indexes a list, anything else is a plain dict key) with no schema or type-checking. Every `value_map` is hand-written against the vendor's actual JSON shape and only ever validated by a human reading it against a sample payload - there's no mechanism that would have caught #13/#14 (two independent paths silently assuming opposite spellings of the same field) before it shipped.

Idea: let a `value_map` element be a tuple/list of alternate keys instead of just one, meaning "try each of these in order, use the first that's present" - e.g. `("preconditioning", "preconditionning")` at the position where the code currently hardcodes one spelling. That's a small, backward-compatible extension to `get_value_from_map` (one `isinstance(key, (tuple, list))` branch), and it directly fixes #13/#14 by making the alternate-spelling handling reusable in the one generic place instead of two independent, inconsistent implementations. A lighter-weight complementary step: a small offline test that runs every `value_map` against one or two captured real API response fixtures and asserts none resolve to `None`, so a future typo gets caught before it ships instead of showing up as a silently-stale sensor.

Expected effects if implemented:
- Fully backward compatible: existing `value_map` entries (plain string/int/dict elements) are untouched; the tuple form is purely additive syntax, so no existing sensor needs to change.
- Design decision that has to be made correctly: "first alternate that's present" must mean *present as a key* (`key in value`, matching the existing dict-key branch's semantics), not "first alternate whose value is truthy". A vehicle can legitimately report an empty/`0`/`False`/`None` value for a real field - treating that as "try the next alternate instead" would skip a genuinely-present field in favor of an unrelated one, which is itself a new instance of the exact bug class this is meant to prevent.
- Larger blast radius than fixing #13/#14 individually: `get_value_from_map` backs *every* sensor and binary sensor, so a mistake in the new alternate-key branch could silently affect many entities at once, not just the one field being fixed. #13's own suggested one-line fix stays narrower and lower-risk by comparison.
- Doesn't fully replace #13's fix: `get_programs()` (#13) doesn't go through `get_value_from_map` at all - it has its own separate lookup logic - so this change would fix #14 but #13 still needs its own dedicated fix regardless.
- Alternate order becomes meaningful and should be commented: if a vehicle's API ever reports *both* spellings at once, whichever key is listed first in the tuple wins - worth a one-line comment at the call site so it reads as a deliberate choice, not an arbitrary one.

### 18. Heavy copy-pasted boilerplate across platform files

`button.py`, `switch.py`, `text.py`, `time.py`, `number.py` - each platform's `async_setup_entry` repeats near-identical per-vehicle entity-description construction, unlike `sensor.py`/`binary_sensor.py` which already build their entities from the table-driven `SENSORS_DEFAULT`/`BINARY_SENSORS_DEFAULT` in `const.py`. Not a bug, just a maintenance tax: adding or changing an entity currently means touching hand-written description blocks in several files with subtly different shapes. No concrete fix idea proposed yet - would need to look at whether all five platforms' entity shapes are regular enough to fit one shared table-driven pattern, or only some of them.

### 19. OTP-related MQTT token failures disable remote commands on the very first failure, with no retry - unlike every other error type

Fixed, but only on the still-unpushed `bugfix-not-ready-yet/mqtt-otp-retry-limit` branch (commit `5fe60e3` "Retry OTP-related MQTT token failures before disabling remote commands", + `-tests`), branched off `upstream/develop` per the usual upstream-PR workflow, not yet pushed to `origin` or opened as a PR.

`stellantis.py`, `scheduled_mqtt_token_refresh` (in `StellantisVehicles`).

`CommunicationError` (transient network failures) gets a proper retry-with-backoff policy via `self._mqtt_token_retry` / `MQTT_TOKEN_RETRY_BACKOFF` before giving up. `ConfigException` and `ConfigEntryAuthFailed` - both raised from the OTP activation/code path - get none: the very first occurrence immediately calls `disable_remote_commands()` and tells the user to fully reconfigure the integration (SMS code + PIN again), with zero tolerance for a one-off hiccup.

Confirmed reachable, not just theoretical: `Otp.activation_start()` (`otp/otp.py:196`) raises `ConfigException(xml)` directly whenever InWebo's `ActionSetup` call returns a non-`"OK"` `err` - this propagates uncaught through `Otp.get_otp_code()` (whose `try/except` only catches `AssertionError`), through the executor job, and up into `scheduled_mqtt_token_refresh`'s `except ConfigException:`. A single bad response from InWebo's server is enough to trigger the instant-disable path.

This is more consequential now that #3 is fixed: before, a failed activation was silently treated as a success (the #3 bug), so this harsh policy rarely actually fired. Now that failures correctly surface as `ConfigException`/`ConfigEntryAuthFailed`, a transient InWebo blip goes straight to "disable remote commands, please reconfigure" instead of being weathered.

Compounding factor: `get_otp_code()` (`StellantisOauth`, the wrapper around the `Otp` object) is rate-limited to 6 calls per day via `@rate_limit(6, 86400)`, and the decorator counts a call against that budget *before* it knows whether the call will succeed (`calls.append(now)` runs before `return await func(...)`). A short burst of transient failures can burn through a meaningful chunk of the daily quota on failed attempts alone, on top of having no retry tolerance.

Fix sketch:
- Add a second retry counter, e.g. `self._mqtt_otp_retry`, initialized to `0` alongside `self._mqtt_token_retry` in `__init__`, and a small constant like `MQTT_OTP_RETRY_LIMIT = 3` in `const.py` (deliberately smaller than `len(MQTT_TOKEN_RETRY_BACKOFF)`, both to recover reasonably fast and to avoid spending too much of the 6/day OTP budget on retries of a single failure).
- Factor the backoff computation into a small helper reused by both except blocks, e.g. `_otp_retry_backoff() -> timedelta | None` that increments `self._mqtt_otp_retry`, returns the next delay (reusing `MQTT_TOKEN_RETRY_BACKOFF`'s first few entries) while under `MQTT_OTP_RETRY_LIMIT`, and returns `None` once exhausted.
- In `except ConfigException:` and `except ConfigEntryAuthFailed as err:`, call the helper: if it returns a delay, log a "attempt N/LIMIT, retrying at ..." warning and schedule `next_run` as usual instead of returning early; if it returns `None`, reset the counter, `disable_remote_commands()`, notify, and (for `ConfigEntryAuthFailed` only) start the reauth flow - exactly like today, just gated behind the exhausted-retries branch instead of firing immediately.
- Reset `self._mqtt_otp_retry = 0` on the success path too (next to the existing `self._mqtt_token_retry = 0`).
- Keep the two `except` blocks separate (don't merge them into one), since only `ConfigEntryAuthFailed`'s give-up branch starts HA's reauth flow - `ConfigException`'s doesn't and shouldn't gain that side effect.

Update 2026-10-07: parked as `bugfix-not-ready-yet/mqtt-otp-retry-limit` (+ `-tests`), rebased onto `upstream/develop` `7f75d7d` as `7cb9015` (tests `8de05a8`); `origin` still has the old `5fe60e3`, so a push would need a force. Not in `testing` any more. Reason: Graylog 2026-08-25 to 2026-10-07 (one instance) has no hit for "MQTT authentication failed", "MQTT authentication error", "OTP code is empty", "OTP file", "Can't get otp code" or "ConfigException", so neither the old instant disable nor the retry ever fired. The only related events are 8 incidents (08-28 twice, 09-09, 09-16, 09-19, 09-28 three times, 10-01) of `400 invalid_grant` on the OTP password grant, every one absorbed by the refresh-token fallback in `refresh_mqtt_token_request`. The "confirmed reachable" above is a code path, not an observed event. Issues #638 and #618 (remote commands vanish) are other users' logs and unconfirmed as coming from this path.

On this path `ConfigEntryAuthFailed` comes from three places: the OTP file is missing (permanent, a retry only burns OTP budget), the OTP code is empty (the server answered something other than OK, maybe transient) and `invalid_grant` on the password grant (ambiguous: a rejected code or a revoked device). The give-up branch starts a reauth, which only renews the OAuth token and does not repair OTP; the real remedy is the `reconfigure_otp` notification (reconfigure with SMS code and PIN). If this is revived: give up at once on a missing OTP file, keep a bounded retry only for the plausibly transient cases and say so in the PR text. Next step offered: read the debug log attached to upstream issue #618 to see which exception actually disabled remote commands there.

### 22. `KWH_CORRECTION = 1.343` is a single global magic number applied to every vehicle

`const.py:52` (`KWH_CORRECTION`), used in `base.py`'s `get_value()` (`battery_capacity`/`battery_residual`, gated by `switch_battery_values_correction`) and in `sensor.py`'s `StellantisLastTripSensor` (electric consumption/avg-consumption divisor). The same fixed ratio is applied regardless of vehicle model or battery pack size, even though the underlying vendor data-quality issue it corrects for (see [issue #272](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/issues/272), and the related #20 above) plausibly varies by e-CMP platform variant/battery capacity.

Not a bug in itself - it's an opt-in, user-toggled correction (`switch_battery_values_correction`) that has apparently worked well enough in practice to stay unchanged since #272. But it's a design smell in the same family as #17: a single hardcoded constant standing in for what should probably be per-vehicle or per-model data. Worth revisiting together with #17/#20 rather than in isolation, since all three touch the same "vendor reports inconsistent/wrong battery data" problem area.

### 23. `StellantisLastChargeSensor` round-trips its attributes through formatted unit strings on every update

`sensor.py`, `StellantisLastChargeSensor.coordinator_update()`. Attributes like `initial_energy`/`final_energy`/`recharged_percent` are stored as strings with the unit baked in (e.g. `"12.5 kWh"`), not as plain numbers. Every call to `coordinator_update()` first strips the unit back off (`attributes[attribute].replace(f" {unit_of_measurement[attribute]}", "")`) so the values can be used in arithmetic, then re-appends it at the end (`f"{attributes[attribute]} {unit_of_measurement[attribute]}"`) before assigning `self._attr_extra_state_attributes`. `StellantisLastTripSensor` does the same thing for its own attributes (`duration`, `start_mileage`, `avg_speed`, etc.).

Not a bug - the round-trip is exact today, since `unit_of_measurement` is a fixed constant dict and the values are always re-serialized the same way they're parsed. But it's an unusual, easy-to-break pattern: it depends on the stored string always containing the *exact* trailing `" {unit}"` substring, breaks quietly if a future change reorders when units get attached, and doesn't match Home Assistant's usual approach of keeping attribute values as plain numbers and letting the unit live in metadata/templates rather than in the value itself. Fix sketch: store the raw numeric value in the attribute and drop the unit suffix entirely (or expose it once via a documented convention), removing both the strip and the re-append step.

### 28. `_LOGGER.exception(...)`'s traceback text is never masked at all

`SensitiveDataFilter.filter()` (`utils.py:335-346`) only rewrites `record.msg` and `record.args` before returning `True`. It never touches `record.exc_info` / the `record.exc_text` that Python's `Formatter.format()` renders from it - so anything logged via `_LOGGER.exception(...)` (implicit `exc_info=True`) has its full traceback, including the innermost exception's own message, emitted completely unmasked, regardless of #27's fix or `anonymize_logs`.

Reachable at multiple call sites already inside the filtered loggers: `stellantis.py:418,825,832,1033,1038,1159,1192,1267,1311`, plus similar ones in `base.py`. By default Python tracebacks don't include local variable values, only file/line/function and the exception's own `str()` per frame - so the practical exposure largely overlaps with #27 (the final exception's message), but through a path neither #27 nor #26 touches.

Fix sketch: more involved than #27, needs prototyping rather than a one-line change. `Filter.filter()` runs before the record reaches a `Formatter`, so `record.exc_text` isn't rendered yet at that point - the filter would need to pre-render it itself (e.g. `record.exc_text = self.formatException(record.exc_info)` via a `logging.Formatter` instance) and mask that string, then leave `record.exc_info` set so the real `Formatter` still uses the now-masked cached `exc_text` instead of re-rendering the original. Needs care not to double-render or interfere with any other handler/formatter already relying on `record.exc_info`/`record.exc_text`'s default (unmasked) behavior.

### 29. No automated test suite anywhere in the fork

Confirmed on `upstream/develop`: zero files under any `tests/`/`test_*` path, and CI (`.github/workflows/hassfest.yaml`, `hacs.yaml`) only validates manifest/HACS structure, never runtime behavior. For ~4800 lines of stateful, concurrent client code (HTTP + MQTT + a hand-rolled OTP crypto protocol) this means every fix, including every one in this file, is verified by manual testing against a real account only - already the documented workflow (`CLAUDE.md`'s Tests section), not an oversight, but still the single biggest quality gap relative to Home Assistant Core or other well-maintained HACS integrations.

Idea: at minimum, cover the parts that need no live HA harness and no real account - `SensitiveDataFilter` (utils.py), `get_value_from_map`/`get_value` (base.py) against captured fixture payloads, `rate_limit`, the migration steps (`__init__.py`) against representative pre-migration `config.data` snapshots. `pytest_homeassistant_custom_component` is already available locally per `CLAUDE.md`. Not something to take on unprompted given the standing per-branch `-tests` workflow, but worth a deliberate decision on how much of it should eventually land upstream rather than staying local-only forever.

### 30. The vendor API client is not decoupled from Home Assistant

`stellantis.py` (1191 lines): `StellantisBase` -> `StellantisOauth` -> `StellantisVehicles` implement OAuth, the HTTP client, the MQTT client, OTP orchestration and ABRP push in one class hierarchy that imports `homeassistant.core.HomeAssistant` and takes `hass` in `__init__`. There is no vendor-API layer that is importable and testable without Home Assistant running - unlike the pattern used by well-structured (often Gold-tier) integrations, which publish a thin, standalone client library and keep the `custom_components`/`homeassistant/components` side a translation shim over it.

Not something to fix in one pass - this is a description of the whole file's shape, not a single bug - but worth naming as the root cause behind several smaller pain points already in this list (#30 below's untyped `_sensors` dict, and why #29 above is hard to retrofit incrementally: a class that only runs inside `hass` is a class that can only be tested inside `hass`).

### 31. `self._sensors` is an untyped, shared, stringly-keyed dict standing in for a data model

`StellantisVehicleCoordinator._sensors` (`base.py`) is read and written from `base.py`, `sensor.py`, `stellantis.py` and every platform's entities alike - regular sensors, restore-sensors, numbers, switches, texts and times all keep their live value in this one dict, keyed by ad hoc strings (`"battery"`, `"switch_battery_charging_limit"`, `"number_refresh_interval"`, ...). There is no schema, so a typo'd or inconsistent key does not fail - it just silently reads back `None`/absent, which is structurally the same failure mode already confirmed twice in this file's "Done" and "Open" sections (#13/#14's `preconditioning`/`preconditionning` split reads and writes different keys depending on which code path touches it).

Idea: not a one-shot fix, but worth considering the direction of travel - a `TypedDict` or small dataclass for the per-vehicle sensor state, built up once per `_async_update_data()` cycle instead of accreted key-by-key across many call sites, would make a class of future bugs like #13/#14 a type-checker error instead of a silent `None`. Large blast radius (every platform file touches `_sensors`), so this is a candidate for a slow, incremental migration rather than a single PR.

### 32. `get_value()` centralizes every sensor's business logic in one generic method

`StellantisBaseEntity.get_value()` (`base.py:610-683`) is one generic method shared by every sensor, and it dispatches on `self._key`/`key` through a long chain of `if key == "mileage"`, `if key == "fuel_consumption_total"`, `if key in ["time_battery_charging_start", "battery_charging_end"]`, `if key in ["battery_capacity", "battery_residual"]`, `if key in [...]` (temperature unit conversion), `if key == 'battery'` - each branch its own unrelated per-sensor transform (unit conversion, Fahrenheit-to-Celsius, charge-limit ETA math, the KWH_CORRECTION multiplier, the `autonomy == 0` battery-100%-bug workaround). Adding, changing or debugging one sensor's transform means reading and reasoning about all of them, and the project's own style guide (root `CLAUDE.md`) already documents the alternative: a `value_fn` lambda/callable per `SensorEntityDescription`, so each sensor owns its own transform independent of the others.

Fix sketch: not urgent (the current form works, this is a maintainability note, not a bug), but a natural companion to any future work on #17 or #31 - moving each `if key == ...` branch into a small `value_fn`-style callable on the matching `const.py` entry would let `get_value()` shrink back to "look up the raw value, apply this sensor's own transform" with no per-sensor knowledge left in the shared method.

### 33. OTP session state is persisted via `pickle`

`otp/otp.py` (`save_otp`/`load_otp`) round-trips the `Otp` object - which holds the InWebo `Kiw`/`Kfact` key material used to derive remote-command OTP codes (see #24/#25 above) - to disk via `pickle`, not a plain data format. `pickle.load` executes arbitrary code embedded in the pickle stream; while the file only exists on `.storage/stellantis_vehicles/{customer_id}_otp.pickle`, i.e. under Home Assistant's own storage directory, and nothing in this integration writes attacker-controlled data there, `pickle` is still the wrong tool for security-sensitive material even at rest - it is also opaque to anything other than this exact Python class definition, which is why `investigation/Stellantis-OTP`'s class rename (`Otp` -> `InweboOTP`, see this file's note on that branch under #24) needed its own explicit pickle-migration step (`f2c734d`) just to keep old files loadable.

Idea: no immediate reproduction of harm (this isn't a confirmed exploit, just a design smell), so not worth a rushed fix, but worth keeping in mind for whenever the OTP module gets touched for something else (e.g. if `investigation/Stellantis-OTP` or a #24/#25 fix ever gets picked back up) - a small explicit `to_dict()`/`from_dict()` on `Otp` serialized as JSON would remove the risk and the rename-migration fragility together.

### 34. Non-critical per-vehicle settings live in `ConfigEntry.data` instead of `ConfigEntry.options`

Per-vehicle UI toggles (ABRP token, charge-limit switch/number, refresh-interval override, notifications) live under `data["vehicles"][vin][...]` and are written via `update_vehicle_stored_config()` (`stellantis.py`), which calls `async_update_entry(data=...)` - not `ConfigEntry.options`, the mechanism Home Assistant provides specifically for exactly this kind of non-connection-critical, user-tunable setting (see the root `CLAUDE.md`: "Non-critical settings: Store in ConfigEntry.options"). It is also very likely the underlying reason the migration chain in `__init__.py` has already been reshaped seven times (`_migrate_to_1_2` through `_migrate_to_20260902`) - several of those steps exist purely to reshuffle where per-vehicle settings live within `data`, a problem `options` (which is not versioned/migrated the same way and is naturally free-form) would not have created in the first place.

Not a one-line fix - `data` vs `options` is a foundational config-entry decision, and every number/switch/text/time entity's `native_value`/`is_on` getters (`base.py`) currently read through `get_vehicle_stored_config()` against `data`, so moving this would touch every one of those platforms plus another migration step. Worth flagging as a structural decision for if/when this area gets a deliberate refactor, not as something to fix incidentally alongside an unrelated change.

### 35. `StellantisBase` owns a private `aiohttp.ClientSession` instead of using Home Assistant's shared one

`start_session()`/`close_session()` (`stellantis.py:150-158`) create and tear down this integration's own `aiohttp.ClientSession()`, rather than using `homeassistant.helpers.aiohttp_client.async_get_clientsession(hass)` - the pattern the root `CLAUDE.md` documents under "WebSession Injection" and the pattern this exact file already uses correctly elsewhere: `resize_and_save_picture()` (`stellantis.py:608`) calls `async_get_clientsession(self._hass)` for its own request. Owning a private session means a separate connection pool from the rest of Home Assistant, and it is the same session this file's own `make_http_request()` tears down and rebuilds on every request error (see #16 above) - a second angle on the same "cascading failure" design smell, since a shared HA-managed session would not need per-error teardown/rebuild logic at all.

Fix sketch: swap `start_session()`'s `aiohttp.ClientSession()` for `async_get_clientsession(self._hass)` and drop `close_session()`'s explicit `.close()` (Home Assistant owns that session's lifecycle). Worth doing together with #16 rather than separately, since #16 already removes most of the reasons `close_session()` gets called from inside `make_http_request()` in the first place.

### 36. `paho-mqtt` is pinned unbounded (`>=1.3`) while the code relies on its legacy callback API

`manifest.json`'s `requirements` lists `"paho-mqtt>=1.3"` with no upper bound, but `MqttClientMod`/`connect_mqtt()` (`stellantis.py`) use the pre-2.0 callback signatures directly (`_on_mqtt_connect(self, client, userdata, flags, result_code)`, 4 arguments; `CallbackAPIVersion.VERSION2` calls back with a 5-argument signature including `properties`), and `mqtt.Client(...)` is constructed here with no `callback_api_version` argument at all. By contrast `Pillow==12.*` in the same `requirements` list is pinned tightly.

Checked 2026-10-06 against paho-mqtt 2.1.0 (the version HA pins in `requirements_all.txt`): this is not a breakage today. `Client(clean_session=True, protocol=MQTTv311)` without `callback_api_version` still works there; paho falls back to `VERSION1` and only emits a `DeprecationWarning` ("Callback API version 1 is deprecated"). The risk is therefore a later paho release that removes that implicit fallback (or a 2.x variant where it is an error), at which point `Client(...)` would fail and remote commands would stop working until the integration is fixed.

Fix sketch: pass `mqtt.CallbackAPIVersion.VERSION1` explicitly as the first argument of `MqttClientMod(...)` in `_connect_mqtt()` (removes the warning and the dependence on the implicit fallback) and raise the pin to `paho-mqtt>=2.0` in `manifest.json`, since `CallbackAPIVersion` does not exist in 1.x; HA's own pin makes that harmless for current installs. `MqttClientMod.__init__` only calls `super()` and can go. The alternative, an upper bound like `<2.0`, would conflict with HA's pin. Low priority: no functional benefit today, a precaution for a future HA/paho bump.

### 38. OAuth could fall back to PKCE instead of a client secret, at least for Opel/Vauxhall

`configs.json`/`const.py` authenticate every brand the same way: `OAUTH_TOKEN_HEADERS`'s `Authorization: Basic base64(client_id:client_secret)` on both the initial code exchange (`get_access_token`) and every refresh (`refresh_oauth_token_request`). All five brands' `client_id`/`client_secret` pairs are static values embedded in the vendor's own mobile apps.

Found while reverse-engineering a third-party reimplementation ("MyStellantis", package `it.stellantis.standalone`, an unofficial Play Store app by an independent developer, not Stellantis) to cross-check this fork's own OAuth constants against the official MyCitroën app. That app's brand table (`it/stellantis/standalone/p154v5/a.java` after decompiling) carries a `usePkce` flag per brand: `false` for Peugeot/Citroën (same client_id/secret pairs as this repo's `configs.json`, confirming both independently), but `true` for Opel, Vauxhall and DS, with DS's `client_id`/`client_secret` both empty strings (DS support in that app looks non-functional, so it's not independent confirmation PKCE actually works for DS; Opel and Vauxhall both have real client_ids though, matching this repo's own). Its token-exchange code (`p170y5/b.java`) branches cleanly on that flag: PKCE sends `client_id` + `code_verifier` with no `Authorization` header at all; the non-PKCE path sends today's Basic-Auth header and no PKCE params. Its authorize-URL builder (`it/stellantis/standalone/auth/OAuthWebViewActivity.java`) adds the standard `code_challenge`/`code_challenge_method=S256` query params alongside the existing `client_id`/`redirect_uri`/`scope`/`locale` ones already used here.

Not a confirmed bug, no reproduction against the real Stellantis backend from this side - just a documented, independently-coded alternative that a real published app apparently relies on for two of the five brands.

Idea, as an opt-in alternative rather than a replacement: add `use_pkce` per brand in `configs.json` (default unset/false, so no existing brand's behavior changes), generate a `code_verifier`/`code_challenge` (S256) pair when `use_pkce` is true and add `code_challenge`/`code_challenge_method` to the authorize URL, and branch `get_access_token()`/`refresh_oauth_token_request()` between today's Basic-Auth headers and a PKCE variant that sends `client_id`+`code_verifier` (and, for refresh, `client_id`) with no `Authorization` header. Needs new, separate `const.py` entries (`OAUTH_AUTHORIZE_PKCE_QUERY_PARAMS`, `OAUTH_GET_TOKEN_PKCE_QUERY_PARAMS`, `OAUTH_TOKEN_PKCE_HEADERS`, `OAUTH_REFRESH_TOKEN_PKCE_QUERY_PARAMS`) rather than changing the existing ones, plus a migration concern for the new `use_pkce` config field on existing installs.

Deliberately not pursued now: this touches the auth path with no automated test coverage (#29) and a real risk of locking users out if PKCE turns out not to actually be accepted the way the third-party app's code implies - there's no evidence today's secret-based flow for Opel/Vauxhall is broken, so this would only be trading a working path for an unverified one. Worth revisiting if Stellantis ever rotates/invalidates one of those two brands' secrets and the existing flow actually breaks, not preemptively.

### 45. Concurrent `scheduled_mqtt_token_refresh` calls can double-refresh and orphan a timer (single-flight idea)

`scheduled_mqtt_token_refresh` (`stellantis.py`) has several callers that can overlap: the scheduled timer, `send_mqtt_message` (every command), the 400 retry in `_on_mqtt_message` (`force=True`) and, if #37 part 2 were ever built, `_on_mqtt_disconnect`. There is no lock around it (`_mqtt_lock` only covers connect/disconnect, see #37). Two overlapping runs can both pass the expiry check before either finishes, so both send the refresh request, and both re-arm `_mqtt_token_scheduled` at the end; the second assignment overwrites the first handle without cancelling it, leaving an orphaned timer (same class as #646/#658). Whether the API rotates the refresh token, which would make the second request fail on a consumed token, is assumed, not verified. Not observed in practice so far; deliberately left alone on 2026-10-06.

Idea (single-flight, preferred over a plain `asyncio.Lock`, which only serializes and still lets a `force=True` caller refresh a second time right after the first): keep at most one refresh task. The body moves to `_mqtt_token_refresh(force)` (including re-arming the timer); the public method starts it only if none is running and awaits it through `asyncio.shield`, so late callers share the running refresh's result instead of starting their own. Needs the task handle cancelled in `async_shutdown`, and a check that `_shutting_down` and `reset_scheduled_mqtt_token` still behave as in #658. Heavier alternative: one long-lived refresher task that sleeps until the next run or a `asyncio.Event`, with all other call sites only setting the event (removes the timer handle problem structurally, but is a bigger rework). Before building either, look in Graylog for two `MQTT token refresh` runs within a few seconds of each other to see if it ever happens.

### 24. `otp/otp.py` logs through a logger the `SENSITIVE_DATA_FILTER` was never attached to

`otp/otp.py:21`, `logger = logging.getLogger(__name__)`. The shared `SENSITIVE_DATA_FILTER` (`utils.py:188-347`) is only attached via `_LOGGER.addFilter(SENSITIVE_DATA_FILTER)` in `stellantis.py:83` and `base.py:49`. `logging.Filter` objects added via `addFilter()` apply only to the exact logger instance they're attached to, not to sibling/child loggers further down the module hierarchy - so `otp/otp.py`'s own logger (`custom_components.stellantis_vehicles.otp.otp`) is never filtered, regardless of what value type is logged or whether "Anonymize personal data on logs" is enabled.

Concrete, reachable leaks at `DEBUG` level:
- `otp.py:285`, `logger.debug("otp code: %s", otp_code)` - the finished OTP code itself, the credential that unlocks MQTT remote-command access.
- `otp.py:154`, `logger.debug(dec_string)` - the decrypted `Kiw`/`Kfact` key material used to derive that code.
- `otp.py:177`, `logger.debug(raw_xml)` (on a parse failure) - the raw InWebo `ActionSetup` response, which per `xml_filtred` at `stellantis.py:191` contains `Kiw`/`Kfact`/`pinmode`.
- `otp.py:130-131`, `logger.debug("%s\n%s\n%s", R0, R1, R2_log)` in `get_r()` - `R0` is `challenge;iwK0;serial` and `R1` is `challenge;iwK1;iwK1`, so every OTP computation logged the session keys `iwK0`/`iwK1` in clear. `iwK1` is also the input of the OTP code itself (`_get_otp_code`: `iwK1:defi:iwsecval`). Found 2026-10-06 while preparing the fix.

Notably, `get_r()` (`otp.py:110-131`) already manually redacts the PIN out of `R2_log` before logging it (`R2_log = R2.replace(self.codepin, "###")`) - evidence the author assumed this logger was covered by the same masking as the rest of the integration. It never has been. The PIN redaction is also what hid the `R0`/`R1` leak above: only `R2` was treated.

Fix, branch `bugfix/otp-log-masking` (local, based on `upstream/develop`, not pushed): the logger gets `SENSITIVE_DATA_FILTER`, the three debug lines with `dec_string`, `raw_xml` and `R0`/`R1`/`R2_log` log only a length or a fixed text instead, and `otp_code` is registered before its debug line. Registering `Kiw`/`Kfact`/`iwK0`/`iwK1` with the filter was not done: dropping the lines is simpler and cannot miss a spelling.

Original fix sketch: give `Otp` (or the module) access to the shared `SENSITIVE_DATA_FILTER` instance and `addFilter()` it onto `otp/otp.py`'s logger too, the same way `stellantis.py`/`base.py` do at import time. Since masking substring-matches *registered* values (see #25), also register `Kiw`/`Kfact` there once decoded, not just `otp_code`.

Status: fixed on `bugfix/otp-log-masking` (3 commits on top of `upstream/develop`, tests on `-tests`), merged into `testing`. Local only, not pushed, no PR yet (as of 2026-10-06).

### 1. `_mqtt_last_request` mixed up commands across vehicles

`stellantis.py:591` (field), `stellantis.py:1198-1209` (retry), `stellantis.py:1276-1277` (write). `_mqtt_last_request` was a single slot per account (`StellantisVehicles`), not per command/vehicle. On a 400 "invalid token" MQTT response the retry logic resolved the right coordinator from `data["vin"]`/`correlation_id`, but replayed whatever `service`/`message` was stored in `_mqtt_last_request` - which could belong to a different vehicle's command if two vehicles had commands in flight at once.

Reproduced directly against the pre-fix code before fixing: delivering a 400 for vehicle A's `correlation_id` while `_mqtt_last_request` held vehicle B's `["/VehCharge", {"type": "immediate"}]` resent B's charge command to A's vehicle.

Fixed and **merged** upstream: [PR #634](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/pull/634), branch `bugfix/mqtt-retry-cross-vehicle-mixup`, merged 2026-09-22. `service`/`message`/a `retried` flag now live per `action_id` in `coordinator._commands_history` (already created there, already bounded by `COMMAND_HISTORY_LIMIT`), and the 400 handler looks up the failing `correlation_id`'s own entry instead of the account-wide field, which is now removed entirely.

### 3. `Otp.get_otp_code()` swallowed a failed activation

`otp/otp.py:268-284`, specifically line 274: `if res != Otp.NOK:`. `Otp.NOK` (`-1`) is never actually returned by `activation_finalyze()` (it returns `Otp.OK`, `Otp.OTP_TWICE`, or a raw error string on failure), so the check was always true even on failure, and the code went on to generate and return a bogus OTP code instead of a clear error.

Fixed and PR'd upstream: [PR #635](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/pull/635), branch `bugfix/otp-swallows-failed-activation`. Condition changed to check for the two real success values (`res in (Otp.OK, Otp.OTP_TWICE)`). Also cherry-picked directly onto `testing` (pushed) since `otp/otp.py` was identical between `upstream/develop` and `testing` at the time.

### 26. `make_http_request`'s failed-request debug log used `resp.url` (a `yarl.URL`) instead of the request's `url` string

`stellantis.py:356` (on `upstream/develop`; still present on `testing`/`local/changes` since this fix hasn't been pulled back yet). `SensitiveDataFilter._mask_value()` only masks `str`/`dict`/`list`/`tuple`/`bytes` (see #24/#25/#27) - a `yarl.URL` falls through unmasked, so any registered secret in the URL (e.g. a vehicle id) showed up in clear text on a failed request, even though the same log line's `headers` dict was masked correctly.

Found while looking into the log attached to upstream issue #629 - a 500 from the vehicle status endpoint logged the full, unmasked vehicle id in the URL path.

Fixed and PR'd upstream: [PR #636](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/pull/636), branch `bugfix/mask-url-in-error-log`. Logs the `url` string already built earlier in the function instead of `resp.url`, matching every other log call in this file. Not yet merged, and not yet pulled into `testing`/`local/changes`.

### 27. Exception objects passed directly as a log argument bypass masking

`SensitiveDataFilter._mask_value()` (`utils.py:349-379`) only recognized `dict`/`list`/`tuple`/`str`/`bytes`/`bytearray`; anything else (including plain `Exception` instances) fell through unchanged at line 379, `return value`. `record.args` is masked once per record, before the final `%s` formatting - so a raw exception object logged via `_LOGGER.warning("...: %s", e)` never had its eventual `str(e)` text checked against the masking patterns, the same class of gap #26/PR #636 fixes for `resp.url` (a `yarl.URL`, not caught by the isinstance chain either).

Several call sites in the filtered loggers passed a raw exception object this way instead of a pre-stringified `str(e)` (which *is* masked correctly, since it's already a plain string by the time the filter runs): `stellantis.py:389,405,410,820,1028,1130,1324`, `base.py:138,215,636`. None of them were confirmed to actually leak a *registered* secret at the time - the messages are mostly generic HTTP/connection/API errors - so this was hardening rather than a confirmed active leak like #24/#25.

Fixed and PR'd upstream: [PR #637](https://github.com/andreadegiovine/homeassistant-stellantis-vehicles/pull/637), branch `bugfix/mask-exceptions-in-log-args`. Added a narrow `isinstance(value, BaseException)` branch to `_mask_value` that returns `self._mask_string(str(value))`, ahead of the final `return value` fallback. Deliberately scoped to `BaseException` only, not "anything else" - `int`/`float` also fall through that same line (e.g. `log_call`'s `duration`/`process_duration` in `utils.py`, formatted with `%.3f` after filtering), and eagerly stringifying those would have broken that formatting with a `TypeError` whenever `anonymize_logs` is on. None of the 10 call sites above needed to change individually - the fix runs on every argument before `%s` formatting, including an exception nested inside a logged dict/list/tuple, which a call-site-by-call-site `str(e)` fix wouldn't have reached.

### 6. `extra_state_attributes["last_updated"]` uses a localized string as the dict key, and its value can go stale independent of that

`base.py:861` (`StellantisBaseSensor`), `base.py:887` (`StellantisBaseBinarySensor`), `time.py:56` (`StellantisBatteryChargingStart`), restore-fixup at `base.py:812-815`. Two separate bugs in the same small area, both around the same attribute.

**a) Localized dict key.** `get_translation(...)` returns the *translated display text* (e.g. `"Last updated"` in English, see `translations/en.json:99-101`), which is then used as the attribute's dict key, not just its value. Effects: `state_attr(entity_id, 'last_updated')` in a template returns `None` (the real key is `"Last updated"`, or whatever the active locale translates it to); the key also changes if the user switches the HA UI language, silently breaking anything relying on it. The maintainer already flagged this as a known rough edge with a `# TODO: remove this check on future release, need to rename the attribute` comment at `base.py:812-815`. The restore-fixup there only recognizes three legacy key variants (`"updated_at"`, `"Updated at"`, `"Aggiornato al"`); any other locale's translated label isn't migrated, so it's copied through as its own stale, never-refreshed leftover key sitting alongside the current one - visible to the user as an apparent duplicate "last updated"-looking attribute with an old value.

**b) Value only refreshes when the sensor's own value changes.** `base.py:871-874` and `base.py:897-900`, `if self.value_was_updated(): ... self._attr_extra_state_attributes[label] = self.get_updated_at_from_map(self._updated_at_map)`. `get_updated_at_from_map` reads an `updated_at`-style field straight out of the vehicle's raw API payload (`self._coordinator.data`) - i.e. it's meant to show *the vehicle's own* reported data timestamp, information HA's native `last_changed`/`last_updated` can't provide since those only track HA's own bookkeeping. But the write is gated behind `value_was_updated()`, which only returns `True` if the sensor's *value* changed since the last check. If the vehicle re-reports the same value with a newer `updated_at` (e.g. "still armed, checked in again 2 hours later"), the attribute is never refreshed, so it displays an increasingly stale timestamp even though fresher data was just polled - undermining the attribute's whole purpose of showing data freshness.

Not directly confirmed from a live example, on closer look: an initial screenshot (an `alarm` binary sensor showing `Zuletzt aktualisiert` at 14:53:36, older than HA's own `Letzte Aktualisierung` at 16:38:39 for the same entity) was first read as evidence of this staleness. But HA core's own `StateMachine.async_set_internal` (`homeassistant/core.py`) only creates a new `State` (bumping native `last_updated`) when NOT `(same_state and same_attr)`; when both are true, it takes an early-return path that only bumps the separate `last_reported` field, leaving `last_changed`/`last_updated` untouched. In that screenshot, `last_changed` and `last_updated` were identical (both 16:38:39), which only happens when `same_state` was `False` - i.e. the binary sensor's own value did change at that poll. That would also have made `value_was_updated()` return `True` in the integration's own code at the same moment, so the custom attribute should have refreshed then too - and 14:53:36 showing up regardless is consistent with that simply being the vehicle's own genuinely-unchanged `alarm.status.createdAt` at that moment, not with the attribute being stuck. So that particular screenshot doesn't actually demonstrate (b) after all; the gating logic itself is still a real bug reachable by inspection (a value that's stable across polls while the API's `updatedAt` for it keeps advancing), just not yet confirmed against a live case.

Incidentally, since the HA-core code above only advances `last_reported` (not `last_changed`/`last_updated`) when state and attributes are both unchanged, that field already gives Home Assistant its own native "polled again, nothing changed" timestamp - conceptually adjacent to what this custom attribute is trying to convey, though it's still HA poll-bookkeeping (when *HA* last asked and got the same answer), not the vehicle's own reported data timestamp, so it doesn't replace the need for (b)'s fix.

**c) The name itself collides with HA's own `last_changed`/`last_updated` concepts.** Even once (a) and (b) are fixed, the attribute is still called `last_updated` - the same name (and, per the translation string, effectively the same displayed label) as HA's own native `last_updated` field, despite meaning something entirely different (the vehicle's own reported data timestamp, not HA's state-write bookkeeping). That's exactly what produced the confusing side-by-side reading in the "Details" GUI panel that prompted this write-up: `Letzte Aktualisierung` (HA-native) and `Zuletzt aktualisiert` (this custom attribute) look like the same concept restated twice, when they're not - a user has no way to tell from the label alone why the two ever disagree.

**d) The displayed label is baked in backend-side, using the instance's system language rather than each viewer's own frontend language.** `stellantis.py:590`, `translation.async_get_translations(self._hass, self._hass.config.language, "entity", {DOMAIN})` - `hass.config.language` is the instance-wide default (Settings → System → General), not the per-user frontend language preference. `get_translation(...)` (a) bakes that one resolved string into the attribute *key* at update time, so on a multi-user installation, every user sees the same backend-chosen language for this attribute regardless of their own profile's language setting - unlike the rest of the entity's own translated name/state, which HA's frontend already renders per-viewer from the shipped `translations/*.json` files using each user's own language (this integration has no `strings.json` - unlike a core HA integration, it ships `translations/*.json` directly with no source-file/build step). This is a direct consequence of (a)'s design (translating in Python to build a key) rather than a separate root cause, but worth calling out since fixing (a) the right way removes it as a side effect: once the dict key is the fixed string, HA's frontend already has native, built-in support for translating attribute names automatically - it looks up `entity.<platform>.<translation_key>.state_attributes.<key>.name` from `translations/*.json` itself, per the viewing user's own language, with no backend translation call needed at all. `get_translation(...)`'s use here becomes entirely unnecessary once (a) is fixed properly.

**e) HA's automatic state_attributes translation is scoped per entity, not shared - so removing the Python-side lookup needs the translation duplicated per entity, not just renamed once.** Confirmed live on `testing`: after (a)-(d)'s fix, the `alarm` binary sensor's attribute showed the untranslated, generically-humanized "Vehicle reported at" instead of the German label, even though a German translation existed. Root cause: HA's frontend resolves a state attribute's display name from `entity.<platform>.<translation_key>.state_attributes.<key>.name` - scoped to *that entity's own* `translation_key` (e.g. `binary_sensor.alarm`), not any shared/central location. The old `get_translation(...)` hack worked for every entity precisely because it always read from one hardcoded path (`entity.sensor.mileage.state_attributes.last_updated`) in Python, regardless of which entity called it - a workaround for this exact per-entity scoping limitation, at the cost of (a)'s and (d)'s bugs. Once that hack is removed, the translation only resolves for entities whose own `translation_key` happens to carry the `state_attributes.vehicle_reported_at` entry - originally just `sensor.mileage`, since that's the one hardcoded path the entries happened to reuse. Every other entity (~57 sensors/binary_sensors/the time entity) fell back to generic key humanization instead of a translation, in any language.

Fix sketch:
- For (a): use a fixed string as the dict key everywhere above instead of the translated label - see (c) below for what that string should be, since it's worth changing at the same time - and drop the `get_translation(...)` call entirely (see (d)): just assign the fixed key directly, no lookup needed. The nontrivial part is the restore path (`base.py:812-815`, only `StellantisRestoreSensor`-based sensors persist attributes across restarts): it needs to normalize whichever of the 14 shipped locales' translated variants an existing installation has stored back to the new fixed key, so upgrading doesn't drop or duplicate the attribute. `StellantisBaseBinarySensor` and `StellantisBaseTime`/`StellantisRestoreEntity` don't persist attributes across restarts, so no migration concern there.
- For (b): update the attribute unconditionally from the current API payload on every `coordinator_update()`, not just inside the `value_was_updated()` branch (which should keep gating `_attr_native_value`, just not the timestamp attribute) - and only overwrite when the API actually returned a value (`get_updated_at_from_map(...)` is not `None`), so a transient gap in one poll's payload doesn't blank out a previously-good timestamp with `None`.
- For (c): rename the attribute's key/translation key away from `last_updated` to `vehicle_reported_at` - matches the existing `position_updated_at` (`<subject>_<verb>_at`) naming shape already used on the device_tracker entity (see (d)'s note on that precedent), names *who* produced the timestamp (the vehicle) rather than just *how* it arrived (avoids a bare `api_reported_at`/`data_updated_at`, which would be accurate but non-distinguishing since everything this integration exposes comes via the API), and - critically - doesn't collide textually with any HA-native field (`last_changed`, `last_updated`, or the newer `last_reported` noted in (b) - deliberately drops "last" for that reason, since "last" is redundant on a single-value attribute anyway and `last_reported_api` would otherwise contain HA's own `last_reported` field name as a literal prefix).
- For (d): no separate code change beyond what (a) already does (drop the manual `get_translation(...)` label lookup, assign the fixed key) - HA's per-viewer translation kicks in automatically as a side effect, *provided* (e) is also addressed.
- For (e): duplicate the `state_attributes.vehicle_reported_at.name` stanza under every affected entity's own `translation_key` (~58 across `sensor`/`binary_sensor`/`time` in `upstream/develop`'s `const.py`), not just `mileage`. Full 9-language duplication (~500+ near-identical JSON blocks) is disproportionate for one diagnostic attribute; the pragmatic split actually implemented: **en, de, fr, it** get the full per-entity duplication (confirmed live: HA's frontend falls back to the `en` string when the active language lacks an entity-specific translation, so even non-en/de/fr/it users get a real, if English, label instead of generic humanization); the remaining 5 locales (es, fi, nl, sl, sv) had their previous `mileage`-only entry removed entirely, since a translation that only worked for one entity out of ~58 was a worse, inconsistent experience than a uniform English fallback everywhere.
- Land (a)/(c)/(d) together but (b) as its own commit even though all four are described together here - (a)+(c)+(d) share the same restore-migration mechanics and translation-file touch, while (b) is an unrelated root cause (update-gating logic) with a different risk profile (pure behavior change, no migration). This repo's commit messages go straight into GitHub release notes (`CLAUDE.md`), where bundling the gating fix in with the rename would be less clear than keeping it separate. (e) landed as two further commits: one adding the per-entity `en` duplication, one for the de/fr/it duplication plus the es/fi/nl/sl/sv cleanup.
