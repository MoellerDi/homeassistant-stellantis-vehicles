# PR: Serialize MQTT client connect/disconnect and guard against a missing client

> **Note:** this file is only a helper for opening the upstream PR. Remove it (drop this last commit) before creating the PR.

## Summary

`connect_mqtt()` and `async_shutdown()` both replaced or tore down `self._mqtt` without any coordination between them, and `send_mqtt_message()` read `self._mqtt` without checking it was even set.

- `get_vehicle_status()` calls `connect_mqtt()` per vehicle coordinator whenever the client looks disconnected, so with more than one vehicle configured, several coordinators can call `connect_mqtt()` at roughly the same time. Before this change, `connect_mqtt()` had a bug in how it decided to recreate its paho client: after tearing an existing client down it re-checked `if self._mqtt is None`, but by that point `self._mqtt` was unconditionally `None` again, since the teardown block had just set it there itself. The `await` in between (`loop_stop()` run in the executor) gave the event loop a real chance to switch to another concurrent `connect_mqtt()` call in that window, so two tasks could end up creating two different clients and both calling `connect()` / `loop_start()` on whichever one `self._mqtt` happened to point to when each task resumed, or a `connect_mqtt()` call in flight could recreate a client `async_shutdown()` had just torn down and was still cleaning up.
- `send_mqtt_message()` called `self._mqtt.publish(...)` directly, with no check that `self._mqtt` is not `None`. If it fires before the first `connect_mqtt()` call ever succeeded, or after the connection dropped and hasn't been retried yet, this raises a plain `AttributeError` that ends up logged as "Unexpected error during MQTT message sending" instead of the actual, expected condition (MQTT is not connected).
- The first version of this fix made `connect_mqtt()` unconditionally tear down and rebuild `self._mqtt` on every call, serialized by a lock. With several vehicle coordinators, that made things worse instead of better: coordinator A's `connect_mqtt()` finishes and starts a fresh connection, but `is_connected()` can still read `False` for a moment right after `loop_start()` (the CONNACK has not been processed by the network thread yet). Coordinator B, which read `self._mqtt.is_connected() is False` earlier and was queued on the lock, then gets its turn and tears that brand new connection down again to rebuild it, before it ever had a chance to settle and receive anything. With enough vehicles polling around the same time (typically right after startup or a reload), this can repeat every cycle and the client never stays up long enough to receive a message, which is the regression this fixes.

This branch carries five commits:

1. `Serialize MQTT client connect and disconnect behind a lock`: adds `self._mqtt_lock` (`asyncio.Lock`) and holds it for the entire teardown+reconnect sequence in `connect_mqtt()` and the teardown-only sequence in `async_shutdown()`, so the two can never operate on a client the other task just replaced or tore down. The duplicated teardown logic (drop `on_disconnect`, `disconnect()`, `loop_stop()` in the executor) is extracted into a `_disconnect_mqtt_locked()` helper that assumes its caller already holds the lock, used by both call sites. The now permanently-true `if self._mqtt is None:` re-check in `connect_mqtt()` is removed, since the client is always freshly recreated after `_disconnect_mqtt_locked()`. The unconditional `disconnect()` call previously guarded by `if self._mqtt.is_connected():` is likewise handled by the helper, which is safe to call whether or not the client is currently connected.
2. `Guard send_mqtt_message against a disconnected MQTT client`: adds the same "connect if needed" check `get_vehicle_status()` already does, plus a follow-up check after the connect attempt (since `connect_mqtt()` can fail, or return early while shutting down, leaving `self._mqtt` unusable). If the client is still not connected at that point, it raises `CommunicationError` (this repo's existing exception for backend/transport failures) with a clear message, instead of letting an unrelated `AttributeError` surface.
3. `Skip rebuilding the MQTT client if a concurrent caller already reconnected`: fixes the regression described above. `connect_mqtt()` gets a `force: bool = False` parameter; once the lock is held, if `force` is not set and the client is already connected, it returns immediately instead of tearing it down. `_on_mqtt_subscribe()`'s 300-second forced reconnect (scheduled when the broker rejects a subscription with QoS `0x80`, even though the transport itself can still look connected) passes `force=True` so it keeps reconnecting unconditionally.
4. `Split connect_mqtt into connect_mqtt and reconnect_mqtt`: a plain boolean `force` argument does not say much at a call site (`connect_mqtt(force=True)` does not read as "always reconnect"). The shared logic moves into a private `_connect_mqtt(force: bool)`, and `connect_mqtt()` / `reconnect_mqtt()` become thin, self-explanatory public wrappers around it (`force=False` / `force=True` respectively), each still decorated with `@log_call` so the debug log shows which one ran. `_on_mqtt_subscribe()` now calls `self.reconnect_mqtt()`.
5. `Move _disconnect_mqtt_locked after connect_mqtt/reconnect_mqtt`: pure reordering, no logic change. `_disconnect_mqtt_locked()` used to sit above `connect_mqtt()`/`reconnect_mqtt()`/`_connect_mqtt()`, so a top-to-bottom read hit the teardown helper before ever seeing the public entry points it supports. It now sits right after `_connect_mqtt()`, the method that calls it, ahead of the paho callbacks.

## Change

`stellantis.py`, `StellantisVehicles`:

- `__init__`: adds `self._mqtt_lock = asyncio.Lock()` next to `self._mqtt`.
- `_disconnect_mqtt_locked()` (new): swaps `self._mqtt` out for `None`, drops its `on_disconnect` callback, disconnects it and joins its network thread (`loop_stop()`) in the executor. Caller must already hold `self._mqtt_lock`.
- `async_shutdown()`: the MQTT teardown block now runs inside `async with self._mqtt_lock:` and calls `_disconnect_mqtt_locked()`.
- `connect_mqtt()` / `reconnect_mqtt()` (public, thin wrappers) / `_connect_mqtt(force: bool)` (the actual implementation): the whole body of `_connect_mqtt` runs inside `async with self._mqtt_lock:`. The `_shutting_down` check moved inside the lock (a task can start before shutdown begins but only get the lock after `async_shutdown()` has already set the flag). Right after that, if `force` is not set and the client is already connected, the method returns `True` without touching it. Otherwise, teardown of any existing client goes through `_disconnect_mqtt_locked()`, then a fresh client is always created, configured and connected.
- `_on_mqtt_subscribe()`: its scheduled reconnect now calls `self.reconnect_mqtt()`.
- `send_mqtt_message()`: before building and publishing the message, connects if `self._mqtt` is `None` or not connected, then raises `CommunicationError` if it is still not usable afterwards. A dedicated `except CommunicationError:` clause logs this as a plain warning (an expected condition) instead of the generic `except Exception:` branch's full exception log.
